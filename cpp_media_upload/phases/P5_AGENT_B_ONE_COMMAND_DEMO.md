# P5 — Agent B: idempotent `./demo.sh` and complete seeded demo

**Owner/model:** Agent B, GPT-6.2 Sol Medium. **Depends:** P3 Docker/VM infrastructure, P4 HTTP readiness, stable P2 gRPC interface merged by master. **Parallel with:** P6 Agent A when no overlapping paths. **Own:** `demo.sh`, `scripts/demo/*`, `.env.demo.example` (coordinate with P3), `docs/DEMO_QUICKSTART.md`, `tests/e2e/demo*`. **Do not edit** CMake/C++ core/HTTP files in this phase.

## Scope and user experience

The Mac user runs one command per operation after authorized setup. `./demo.sh start` establishes readiness and the local GUI, `./demo.sh` runs the complete seeded demo and leaves it running, `./demo.sh stop` safely reclaims both MediaDock guests, and `./demo.sh status` reports state read-only. The approved [lifecycle contract](../docs/07_ONE_COMMAND_DEMO_SPEC.md) defines safe shutdown, required evidence and ownership. All four modes work from a fresh terminal without interactive passwords or sudo prompts.

## macOS SSH tunnel lifecycle

In the preferred libvirt topology the Mac cannot ordinarily route directly to `192.168.122.0/24`-style guest NAT addresses. Make `./demo.sh` establish/manage SSH forwarding to the **actual** VM2 private HTTP endpoint through the Ubuntu laptop (using a tested hop with `ssh -J`, or forwarding via laptop to guest). If `127.0.0.1:8080` is busy with a foreign process, fail with clear instructions or choose a configured alternate; never kill unrelated processes. Persist an owner-restricted, deployment-specific SSH control socket or equally verifiable ownership record; confirm it forwards the intended service by checking a distinctive `/health` response. Rerunning `./demo.sh` must reuse/repair its own tunnel. `status` reports tunnel health without creating it. `stop` closes only the validated MediaDock tunnel after graceful guest shutdown. An initial laptop login/password/ssh-key setup is a one-time prerequisite, not demo-day work.
